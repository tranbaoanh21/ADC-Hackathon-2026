## 4. Bốn nhóm khuyết tật và mức phù hợp với team

> Các ví dụ dưới đây chỉ là **problem-space inspiration**, không phải brief chính thức và không đại diện cho nhu cầu của tất cả mọi người trong một nhóm.

### 4.1. Visual Impairment — Ưu tiên số 1

Một số workplace barriers có thể gặp:

- Dashboard hoặc chart không tương thích screen reader.
- Slide có nhiều hình ảnh nhưng thiếu mô tả.
- Screen-sharing diễn ra nhanh và không có visual description.
- Tài liệu scan hoặc PDF thiếu semantic structure.
- UI phụ thuộc vào màu sắc hoặc tương tác chuột.
- Biểu đồ được mô tả quá dài, không theo mục tiêu công việc.
- Thông tin visual trong buổi họp không được chuyển thành dạng dễ điều hướng.

#### Vì sao phù hợp với team?

**Hồng Phúc** có:

- multimodal image–text learning;
- CNN, ResNet, Transformer và Swin Transformer;
- kinh nghiệm sinh báo cáo từ ảnh;
- model evaluation và failure analysis.

**Bảo Anh** có:

- React/Next.js accessible interface;
- Node.js/Express API;
- RAG, embeddings và data retrieval;
- deploy, Docker, AWS và error handling;
- khả năng biến AI inference thành user workflow.

**Phương Linh** có:

- research và structured problem solving;
- stakeholder communication;
- proposal, roadmap và pitch;
- khả năng mô tả impact trong workplace context.

#### Hướng sản phẩm tiềm năng A — Accessible Meeting Visual Assistant

```text
Shared screen / screenshot / chart
               ↓
       Visual preprocessing
               ↓
        Multimodal AI/OCR
               ↓
 Structured, task-aware description
               ↓
 Screen-reader-friendly UI / speech
               ↓
 User asks for detail or navigates sections
```

Không nên chỉ trả về một paragraph mô tả ảnh dài. Output tốt hơn có thể gồm:

```json
{
  "contentType": "bar_chart",
  "title": "Quarterly Revenue by Region",
  "mainInsight": "The South region has the highest revenue.",
  "comparisons": [
    "South is approximately 18% higher than North",
    "Central has the lowest value"
  ],
  "uncertainties": [],
  "availableActions": [
    "Read data points",
    "Compare two regions",
    "Summarise trend"
  ]
}
```

#### Hướng sản phẩm tiềm năng B — Accessible Document Transformation

```text
PDF / slide / scan
        ↓
OCR + layout/structure extraction
        ↓
Image/chart descriptions
        ↓
Heading hierarchy + plain text + alt text
        ↓
Accessible HTML / structured document
```

Phải scope hẹp, ví dụ chỉ tập trung vào onboarding document hoặc internal training material, thay vì “chuyển mọi tài liệu trên thế giới thành accessible”.

#### Công nghệ có thể chuẩn bị

| Thành phần | Lựa chọn nhanh | Lựa chọn nâng cao nếu cần |
|---|---|---|
| Frontend | React hoặc Next.js | Next.js với server actions/API routes |
| Accessibility | Semantic HTML, ARIA đúng chỗ, keyboard navigation | Screen-reader testing, live regions |
| Backend | Node.js/Express hoặc Next.js server | Node gateway + Python AI service |
| Vision | Multimodal API | Pretrained vision-language model |
| OCR | Cloud OCR hoặc open-source OCR | OCR + layout analysis |
| AI output | Structured JSON | Schema validation + confidence/uncertainty |
| Speech | Browser TTS hoặc TTS API | Custom voice preferences |
| Persistence | Không cần hoặc local/session state | PostgreSQL nếu workflow thật sự cần history |
| Deploy | Platform team đã quen | Docker/AWS chỉ khi thực sự có lợi |

#### Accessibility requirements bắt buộc

- Tất cả chức năng chính dùng được bằng keyboard.
- Focus indicator rõ ràng.
- Form control có label.
- Button/icon có accessible name.
- Heading hierarchy hợp lý.
- Status “đang xử lý/đã hoàn tất/lỗi” được screen reader đọc.
- Không dùng màu làm tín hiệu duy nhất.
- Output có thể điều hướng theo section thay vì một đoạn text rất dài.
- Có cách yêu cầu đọc lại, rút gọn hoặc mở rộng chi tiết.
- Không tự động phát audio gây mất kiểm soát.

#### Rủi ro AI cần giải quyết

- Hallucinate số liệu trong chart.
- OCR đọc sai text.
- Mô tả bỏ qua context quan trọng.
- AI khẳng định quá chắc chắn.
- Ảnh hoặc tài liệu nội bộ chứa dữ liệu nhạy cảm.
- Latency quá cao trong live meeting.

Guardrails nên có:

- Đánh dấu uncertainty.
- Hiển thị nguồn input.
- Cho phép người dùng yêu cầu xác nhận data point.
- Không tự động đưa quyết định quan trọng thay người dùng.
- Không lưu file nếu không cần.
- Demo bằng dữ liệu không nhạy cảm.
- Có cached result khi external API lỗi.

### 4.2. Neurodivergence — Ưu tiên số 2

Neurodivergence có thể bao gồm nhiều profile khác nhau như autism hoặc ADHD. Không được giả định mọi người có cùng nhu cầu.

Một số workplace barriers có thể gặp:

- Instruction mơ hồ.
- Không rõ priority hoặc deadline.
- Context switching liên tục.
- Information overload.
- Onboarding material quá dài hoặc thiếu cấu trúc.
- Interview không predictable.
- Expectation hoặc social convention không được nói rõ.
- Sensory/cognitive load từ giao diện và notification.

#### Vì sao phù hợp với team?

- Bảo Anh và Hồng Phúc đều có kinh nghiệm RAG, embeddings và vector search.
- Hồng Phúc có NLP/LLM, prompt engineering và robust AI awareness.
- Bảo Anh có thể xây workflow app hoàn chỉnh rất nhanh.
- Phương Linh có trải nghiệm onboarding, guideline, planning, organizational process và stakeholder communication.
- Team có thể kết hợp cả góc nhìn employee và employer thay vì chỉ làm một chatbot cá nhân.

#### Hướng sản phẩm tiềm năng A — Structured Work Instruction Assistant

```text
Manager message / email / task description
                   ↓
         LLM structured extraction
                   ↓
Goal / Definition of Done / Priority / Deadline
Dependencies / Ambiguities / Clarification questions
                   ↓
Predictable, low-overload interface
                   ↓
User reviews and confirms; AI does not decide silently
```

Ví dụ output:

```json
{
  "goal": "Prepare the monthly performance report",
  "definitionOfDone": [
    "Use the approved report template",
    "Include revenue and customer-retention data",
    "Send a draft to Marketing for review"
  ],
  "deadline": null,
  "priority": "unknown",
  "dependencies": ["Marketing feedback"],
  "ambiguities": ["The deadline is not specified"],
  "clarificationQuestions": [
    "What date and time should the first draft be completed?"
  ]
}
```

#### Hướng sản phẩm tiềm năng B — Accessible Onboarding/Training Assistant

```text
Internal policy / onboarding document
                  ↓
Document retrieval + structure extraction
                  ↓
Plain language / step-by-step / optional detail
                  ↓
Personal preference, not medical diagnosis
                  ↓
Employee feedback + manager clarification workflow
```

RAG chỉ nên dùng nếu cần trả lời dựa trên tài liệu nguồn. Nếu chỉ cần chuyển một instruction thành structure, structured LLM output đơn giản sẽ nhanh và ít phức tạp hơn.

#### Công nghệ có thể chuẩn bị

| Thành phần | Lựa chọn phù hợp |
|---|---|
| Frontend | React/Next.js, predictable layout, low cognitive load |
| Backend | Node.js/Express hoặc Next.js server |
| AI | LLM với structured output và JSON schema |
| Knowledge | RAG/embeddings chỉ khi cần organizational documents |
| Validation | Schema validation, required fields, ambiguity detection |
| Preference | User-controlled verbosity, layout và notification |
| Database | Chỉ dùng nếu cần lưu preference/history |
| Responsible AI | Consent, privacy, no diagnosis, human review |

#### UX/accessibility requirements

- Wording trực tiếp và nhất quán.
- Một nhiệm vụ chính trên mỗi màn hình.
- Progressive disclosure: thông tin cốt lõi trước, chi tiết tùy chọn sau.
- Không animation hoặc notification không cần thiết.
- User kiểm soát độ dài output.
- Không mặc định rằng “đơn giản hơn” luôn tốt cho mọi người.
- Có thể sửa trực tiếp AI output.
- Hiển thị rõ nội dung nào do AI suy luận và nội dung nào lấy từ source.
- Không dùng dark pattern hoặc ép user cung cấp diagnosis.

#### Rủi ro AI và đạo đức

- Tạo ra lời khuyên sai về công việc.
- Biến preference thành medical profiling.
- Khái quát hóa về autism hoặc ADHD.
- Làm người dùng phụ thuộc vào AI để hiểu mọi communication.
- Lưu trữ message nội bộ nhạy cảm.
- Employer dùng tool để “sửa” người neurodivergent thay vì cải thiện môi trường.

Nguyên tắc:

> Sản phẩm nên giúp thay đổi thông tin, workflow hoặc environment để dễ tiếp cận hơn; không nhằm “normalise” hoặc chẩn đoán con người.

### 4.3. Deaf or Hard of Hearing — Khả thi nhưng không ưu tiên

Problem spaces:

- Live caption.
- Speaker identification.
- Meeting question/decision/action item extraction.
- Notification thay thế âm thanh.
- Training video caption và transcript.

Team có thể làm bằng STT API + LLM + accessible UI, nhưng CV chưa cho thấy kinh nghiệm Speech AI hoặc speaker diarization. Nếu được phân công nhóm này, ưu tiên dùng pretrained service/API thay vì tự train model.

### 4.4. Mobility Impairment — Ít lợi thế nhất

Problem spaces:

- Alternative input.
- Voice control.
- Adaptive workstation.
- Switch input.
- Physical navigation.
- Assistive device.

Team có thể xử lý phần software như voice control hoặc accessible remote-work interface, nhưng thiếu mechanical, embedded, sensor và fabrication. Không nên chọn nếu chưa có lý do user-centred rất mạnh.

## 6. Tiêu chí chấm và cách chứng minh

### 6.1. Innovation & Impact

**Official meaning:** mức độ nguyên bản và tác động khi giải quyết accessibility/employability challenge thật.

Giám khảo có thể muốn biết:

- Barrier có thật không?
- Xảy ra ở workplace moment nào?
- Existing solution thiếu gì?
- Tần suất và hậu quả ra sao?
- Solution cải thiện outcome nào?
- Có thể đo before/after không?

Evidence nên có:

- user quote hoặc observation;
- competitor comparison;
- before/after workflow;
- time saved, steps reduced hoặc participation improved;
- một điểm khác biệt rõ, không phải danh sách 15 tính năng.

### 6.2. User-Centred Design & Accessibility

**Official meaning:** mức độ hiểu user needs và áp dụng inclusive/accessible design.

Evidence mạnh:

- “Ban đầu team nghĩ A, nhưng end-user feedback cho thấy B quan trọng hơn, nên team đổi thiết kế.”
- “User muốn output ngắn theo section thay vì một đoạn văn.”
- “Keyboard test phát hiện focus order sai và team đã sửa.”
- “Team loại bỏ feature X vì tăng cognitive load.”

Nguyên tắc:

> **Nothing about us without us** — xây cùng cộng đồng, không chỉ xây cho cộng đồng.

### 6.3. Feasibility & Practicality

Cần trình bày:

- công nghệ đang dùng;
- latency và API dependency;
- chi phí ước tính;
- privacy và data handling;
- khả năng tích hợp workplace;
- adoption barrier;
- limitation;
- roadmap từ prototype đến pilot.

Không nên nói “AI hiểu chính xác 100%”. Nên nói rõ phạm vi, uncertainty và human confirmation.

### 6.4. Use of AI

AI được khuyến khích, nhưng phải:

- effective;
- appropriate;
- responsible;
- ethical;
- meaningful.

Ba câu team bắt buộc trả lời:

1. **Why AI?** Tại sao bài toán này cần AI?
2. **Why this AI?** Tại sao chọn model/API/pipeline này?
3. **What can go wrong?** AI có thể sai ở đâu và team giảm rủi ro thế nào?

AI không meaningful nếu chỉ thêm chatbot hoặc nhãn “Powered by AI” trong khi rule-based logic đã đủ.

### 6.5. Presentation & Communication — Finale only

Giám khảo xem:

- problem có rõ không;
- story có human và workplace context không;
- demo có dễ hiểu không;
- argument có logic không;
- team có thừa nhận limitation không;
- Q&A có trực tiếp và nhất quán không.

Phương Linh là pitch lead, nhưng cả ba phải chuẩn bị trả lời phần mình sở hữu.

### 6.6. Self-scorecard trước khi submit

Chấm mỗi dòng từ 0–5:

| Câu hỏi | Điểm |
|---|---:|

| Barrier có evidence không? | /5 |

## 10. Cách Bảo Anh và Hồng Phúc phối hợp

Không chia kiểu “Anh làm app, Phúc làm model, cuối ngày mới ghép”. Hai người phải thống nhất interface từ đầu.

### 10.1. API contract first

Ví dụ:

```http
POST /api/analyse
Content-Type: application/json
```

```json
{
  "inputType": "image",
  "task": "describe_chart",
  "content": "<uploaded-file-reference>",
  "preferences": {
    "verbosity": "concise",
    "outputMode": "screen_reader"
  }
}
```

Response:

```json
{
  "status": "success",
  "result": {
    "summary": "...",
    "sections": [],
    "uncertainties": [],
    "suggestedActions": []
  },
  "metadata": {
    "processingTimeMs": 1840,
    "model": "...",
    "fallbackUsed": false
  }
}
```

Lợi ích:

- Anh build UI bằng mock response ngay.
- Phúc thay model/prompt mà không làm vỡ frontend.
- Có thể validate schema.
- Cached fallback dùng cùng format.
- Dễ giải thích architecture cho judge.

### 10.2. Suggested architecture A — nhanh nhất

```text
React/Next.js UI — Bảo Anh
          ↓
Node/Next server — Bảo Anh
          ↓
External AI API/prompt/schema — Hồng Phúc
          ↓
Structured result
```

Dùng khi external multimodal/LLM API đủ tốt.

### 10.3. Suggested architecture B — khi cần Python model

```text
React/Next.js UI — Bảo Anh
          ↓
Node/Express gateway — Bảo Anh
          ↓
Python/FastAPI inference — Hồng Phúc
          ↓
Pretrained model/pipeline
```

Chỉ thêm Python service nếu cần thư viện/model Python. Không tách service chỉ để architecture trông phức tạp.

## 13. Accessibility fundamentals

### WCAG POUR

#### Perceivable

- Image có text alternative.
- Video có caption.
- Contrast đủ.
- Không truyền thông tin chỉ bằng màu.

#### Operable

- Dùng keyboard được.
- Không keyboard trap.
- Focus rõ.
- Target đủ dễ thao tác.

#### Understandable

- Wording rõ.
- Flow predictable.
- Error message dễ hiểu.
- Tránh cognitive overload.

#### Robust

- Semantic HTML.
- Tương thích screen reader/assistive technology.
- Accessible name/role/state đúng.

Tham khảo:

- [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- [W3C WCAG Overview](https://www.w3.org/WAI/standards-guidelines/wcag/)
- [How People with Disabilities Use the Web](https://www.w3.org/WAI/people-use-web/)

- [ ] Có fallback khi AI/API lỗi.
- [ ] Có cách giải thích cost, latency và deployment.

## 15. Những bẫy team cần tránh

### Generic disability chatbot

Judge có thể hỏi: “Tại sao không dùng ChatGPT?”

Phải có workflow cụ thể, accessible interaction và improvement rõ.

### Super app

Không làm đồng thời:

```text
Chatbot + CV + TTS + RAG + Job board
+ Interview + Calendar + Social network
```

### Tech-first

Không chọn problem chỉ vì team biết Swin Transformer, RAG hoặc AWS.

### Over-engineering

Không cần Kubernetes, nhiều microservice, queue hoặc database nếu demo flow không cần.

### Product không accessible

App cho người khiếm thị nhưng không dùng keyboard/screen reader được sẽ gây phản tác dụng.

### Tự tưởng tượng user needs

Giả định phải được ghi lại, hỏi và validate.

### Ignore AI risk

Không che limitation. Responsible handling có thể tăng credibility.

### Lệch employability

Mọi solution phải nối rõ với một trong các bối cảnh:

- hiring;
- interview;
- onboarding;
- training;
- meeting;
- communication;
- task execution;
- workplace participation/performance.

## 17. Intellectual Property và Terms & Conditions

**[OFFICIAL]**

- Submission phải là original work của team.
- Plagiarism, sử dụng trái phép third-party IP hoặc sao chép existing solution có thể dẫn tới disqualification.
- Team tự chịu trách nhiệm không vi phạm copyright, trademark, patent hoặc trade secret.
- Mọi IP trong idea, concept và solution vẫn thuộc về participants.
- BTC không yêu cầu chuyển giao ownership.
- Team thừa nhận các đội khác có thể độc lập phát triển idea tương tự.
- BTC không chịu trách nhiệm cho tranh chấp ownership/similarity/commercial use.
- Việc phát triển, thương mại hóa hoặc lập startup sau sự kiện là quyết định và rủi ro của team.

### Quy tắc nội bộ về code/assets

- Chỉ dùng library/model/dataset có license phù hợp.
- Ghi attribution khi license yêu cầu.
- Không copy nguyên một solution có sẵn.
- Không dùng image/video/music không rõ quyền sử dụng.
- Không commit API key hoặc dữ liệu cá nhân.
- Phân biệt rõ generic starter code với solution code phát triển cho brief.

**[TO CONFIRM tại briefing]:**

- Mức độ cho phép generic starter repository.
- Quy định về AI-generated code.
- Quy định khai báo pretrained model/external API.
- Có bắt buộc trích dẫn dataset/model/library trong deck không.
- Submission file format và deadline giờ/phút cụ thể.
- Internet/API access và power/network tại địa điểm.

### ADC 2024 — The Great Musica

Quán quân xây website thư viện bản nhạc Việt bằng Braille cho người mù/khiếm thị và hỗ trợ chuyển standard music sheet.

Bài học:

- Website vẫn có thể thắng.
- Hardware không bắt buộc.
- Specific accessibility need quan trọng hơn tech stack phức tạp.

### ADC 2024 — Lexopia

Á quân là ba sinh viên Business, xây app hỗ trợ dyslexic professionals trong đọc/viết, sử dụng Microsoft Azure AI và Copilot.

Bài học:

- Không bắt buộc tự train model.
- Existing AI service có thể tạo solution mạnh nếu problem/product đúng.

### ADC 2025 — AllStep

Quán quân xây smart walker cho người cerebral palsy, tích hợp smart braking và computer vision. Idea xuất phát từ trải nghiệm thật trong gia đình thành viên.

Bài học:

- Lived experience và community engagement là lợi thế lớn.
- Công nghệ phục vụ một mobility problem rất cụ thể.

### ADC 2025 — NeuroAICC

Á quân xây bilingual web platform hỗ trợ autistic adults chuẩn bị job interview, đồng thời có resource cho caregiver và employer. Team gồm hai Software Engineering và một Digital Communications/Multimedia Design member, co-create với autistic individuals, caregivers và professionals.

Bài học:

- Cấu hình gần với team hiện tại.
- User co-creation và empathy-driven design tạo khác biệt.

### ADC 2025 — 7 Rings và InSight

- 7 Rings: web platform dịch Vietnamese sign language ↔ speech theo thời gian thực.
- InSight: AI-powered app hỗ trợ visually impaired employees trong workplace interaction.

Specific user

+ appropriate technology
+ working prototype
+ validation
+ impact
= strong ADC solution
